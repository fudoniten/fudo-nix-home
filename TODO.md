## Locket does not deploy anything yet

`bin/locket*` works: it creates profiles, encrypts to profile public keys, and
writes the `.age` plus `.json` pair. The Nix module works too, in the sense that
it generates the decrypt and cleanup scripts, the path unit and the cleanup
unit. The two have never been connected.

### 1. Nothing populates `locket.secrets`

`modules/locket/options.nix` documented `locket.secrets` as "usually populated
automatically from `secrets/<user>/`". No such code exists — there is no
`builtins.readDir` anywhere in this repo. The decrypt script is generated by
mapping over `cfg.secrets`, so with nothing in it, the script decrypts nothing.

Write the scan: read `secrets/<user>/*.json` for each user being configured,
pair each with its `.age` sibling, and produce the `locket.secrets` attrset.
Points to settle while doing it:

- **Which user's directory.** The module is per-user Home Manager config, so
  `config.home.username` is the obvious key, but `users/<name>.nix` and
  `secrets/<name>/` are not guaranteed to agree (`config-user` in `module.nix`
  lets one user run another's config).
- **`source` is `types.path`**, so each `.age` lands in the Nix store. That is
  fine — it is ciphertext — but it means a rotation changes the closure. Worth
  knowing before it is a fleet.
- **Validation.** A `.json` naming a profile that does not exist, or an `.age`
  with no `.json`, should fail evaluation rather than silently skip. `locket
  check` already implements exactly these rules; the Nix side should not
  reimplement them differently.

### 2. Nothing is set up

No profile exists (`secrets/` holds only `profiles/.gitkeep`), no secret has
been added, and no host sets `locket.enable`. Once (1) lands:

- `locket profile-create default` — secrets wanted everywhere, including work
- `locket profile-create work` — work-only, so `default` can be excluded there
- per-host or per-class profiles as needed

Deciding the profile set is the part that is hard to change later; the rest is
mechanical.

### 3. The decrypt never re-runs after a config change

`locket-secrets.path` triggers on a key *appearing* in `keyDirectory`. With the
keys already in place — the normal case on a machine you use — a secret added or
retargeted since the last login does not deploy until the next one. Either set
`systemd.user.startServices` or start `locket-decrypt.service` from a Home
Manager activation entry. Marked in `modules/locket/default.nix`.

### 4. Cleanup is both too weak and too strong

- Too weak: `locket-cleanup.service` is `WantedBy = exit.target`, which is
  reached when the user's systemd instance shuts down. That does not happen on a
  host with `loginctl enable-linger`, so the secrets outlive the session.
- Too strong: the `copy` branch removes `$HOME/<target>` unconditionally,
  whether or not locket placed it. The `symlink` branch correctly checks that
  the link points into the runtime directory first; `copy` needs an equivalent.

Both marked in `modules/locket/default.nix`.

### 5. Aegis overlap is undecided

`aegis` (the fleet's system secrets manager) has a user-secrets path of its own,
also unfinished — see `aegis/TODO.md`. The two are complementary: aegis is
admin-mediated and host-keyed and reaches only Fudo hosts; locket is user-keyed
and reaches work and non-NixOS machines. Before either is turned on, settle:

- Which system owns a given secret, and how that is obvious from where it lives.
- What happens when both declare the same target path.
- Whether the two CLIs stay separate or get one front end.

## Backlog

Worth doing, but only once the above works — these all assume a running system.

- **Package the CLI.** `bin/locket*` uses `nix-shell` shebangs, which costs
  ~1-2s on first run. A `pkgs.locket` derivation would remove that and make the
  tools installable via `home.packages`.
- **`locket-remote`.** Clone the repo, edit a secret, push a branch, open a PR,
  so secrets can be changed from a host without a full checkout. Previously
  specified here in some detail; the detail was speculative and has been dropped
  rather than kept as if it were a plan.
- **Documentation.** A migration guide from agenix/sops-nix, and disaster
  recovery (what to do when a profile key is lost — today, nothing, since the
  key is the only copy).
